# ADR-004: Session debits in batches, a receipt event per thought

**Status:** Accepted (the user's decisions 2026-10-27: OD-5 «Одно списание за сессию»; critic MAJOR 5 «Событие в журнале транзакции»; 2026-10-28: add-pet critic MAJOR 3 «Только +1 к предыдущему»); amended 2026-10-29 — a thought paid by usage (see «Paid by usage, 2026-10-29»); amended 2026-10-29 — at most 12 thoughts a batch (the user, build add-pet critic MINOR 3: «Вписать в спеку»; see «Batches of at most 12, 2026-10-29»); amended 2026-11-03 — up to four calls a receipt and batches bounded by log bytes (the `add-pet-errands` build; see «Four calls a receipt, batches by log bytes, 2026-11-03»)
**Date:** 2026-10-27; amended 2026-10-29, 2026-11-03
**Deciders:** the user

## Context
Every thought costs the pet food. A transaction per thought costs gas each time; one per session amortises it (§4 › Цена мысли). Each thought must leave a public receipt: the request and response hashes, the signature and the model id (§3 › Отличие). State costs storage stake; NEP-297 events cost gas only, ≤100 logs and ≤16 kB per receipt (`near-contract` › State vs events).

## Decision
- `debit_session` is called by the server account only, once or more per session (batches of at most 12 thoughts, below); each call is accepted whole or rejected whole.
- Each batch carries a `debit_id`; the contract keeps the last accepted one in the pet's record (0 at mint) and accepts only a batch whose `debit_id` is exactly one above it. A batch resent while its outcome was unknown is never debited twice (add-pet critic MINOR 7, the user, 2026-10-27: «Контракт отклоняет повтор»), and a jump is rejected the same way (add-pet critic MAJOR 3, the user, 2026-10-28: «Только +1 к предыдущему»): with «any greater id» a stolen server key could send a batch with `debit_id` = u64 max and every honest batch of that pet would be rejected as a replay for good, revoking the key would not fix it. The `debit_id` is in every receipt event. Decided by default: one number per pet rather than a set of seen ids — fixed storage paid at mint, no stake per session; a rejected batch does not move the number, so the next batch reuses it; the server sends a pet's batches one at a time and reads the last accepted number from the contract before sending (build `design.md`).
- Caps checked by the contract for every thought in the batch: ≤ 0.005 NEAR a thought, ≤ 0.05 NEAR a pet per UTC day by `block_timestamp`, never more than the pet's food.
- Each thought is a NEP-297 event: token id, model id, price, sha256 of the request bytes, sha256 of the response bytes, signature, signature kind (`provider_tee` | `gateway`), signing address. Nothing per thought is kept in contract state.
- The debited sum goes to the project's treasury account in the same call.
- A stolen server key can still send the next number with a capped batch; honest batches sent with the same number are then rejected and paid by the project until the server re-reads the number — no lasting lock, and revocation ends it.
- Decided by default: the contract records the NEAR AI signature and does not verify it. NEAR AI signing keys rotate when a replica restarts (`near-ai` › Volatile), so an on-chain list of allowed signers would reject honest debits after every rotation; anyone can verify the signature off chain (`add-verification`).

## Consequences
- The on-chain balance lags the session; the server shows fullness as food minus the session's not-yet-debited thoughts (`Pet food data`).
- A rejected debit leaves the delivered thoughts unpaid: the project absorbs them — except a batch rejected for a hire record, which is resent without it (ADR-011). One pet's spends are served one at a time and each price is reserved in the unbilled sum before the NEAR AI call (`Thought queue data`; the user, 2026-10-28, Final critic Attacker MAJOR 1), so parallel tabs or scripts cannot push the unbilled sum past the food or the daily cap and get a batch rejected on the sum.
- A session of more than 12 thoughts is split into several debits, sent one at a time in `debit_id` order (below).
- A session closes after 10 minutes without a thought and always at 00:00 UTC (critic MINOR 10, 2026-10-27); a batch executed after midnight counts in the new UTC day for the server as for the contract (`Pet food data`).
- The daily diary thought is paid from the pet's food like a cheap thought; without an owner's session that day it is its own debit, its gas beyond the share in the price paid by the project (§4).
- A `gateway` signature (streaming fallback, OD-7) is recorded with its kind and is never presented as proof that the model produced the answer.

## Paid by usage, 2026-10-29
The user's decisions at Init fix (2026-10-29): «должно быть гибко» + «Да, платит по факту» — the pet pays every thought by what it used; «ПРОЕКТ НИХУЯ НЕ ПОДОПЛАЧИВАЕТ» (OD-1470); OD-1501 → «Переспросить без рассуждения»; OD-1502 → «Наниматель по факту»; the round's defaults («Принимаю все 9»). Everything above stands except where this section says otherwise.
- **The price of a thought** is computed by the server from the `usage` of its own response: (`usage.prompt_tokens` × in + `usage.completion_tokens` × out) × 1.2 + the gas share ≈ $0.0006, converted to yocto at the server's NEAR→USD setting (PRODUCT.md §4 › Цена мысли). Reasoning tokens are inside `completion_tokens` (`usage.completion_tokens_details.reasoning_tokens`) [fact: REVIEW_LOG.md, 2026-10-29 · Init fix · the 18 test calls]; the signed response bytes carry the same `usage`, so the owner can check a receipt's tokens against its bytes.
- **The contract takes a variable price.** It never knew a fixed price of a thought: it checks each receipt's price ≤ 0.005 NEAR, the day ≤ 0.05 NEAR and the food — unchanged. It does not recompute the price from the tokens (the rates and the NEAR→USD setting are the server's); a stolen server key can write any price under the caps, as it could before.
- **What a receipt records, added:** the price is the exact one; per call — the input, output and reasoning tokens and whether the call was cut at its ceiling (`finish_reason` = `length`). Decided by default, not an open question: the exact price was already public and output tokens dominate it (34× the input rate), so answer length was already readable from the price; the tokens add only the split of reasoning vs answer. Gas only, no state.
- **One receipt, one or two calls.** A «Think hard» whose reasoning reached its ceiling with no line is re-asked at once on the same model without reasoning (OD-1501 A); the thought's one receipt carries both calls — each with its hashes, signature, kind, signer and tokens — and one price, both calls' tokens with one gas share (the product-lead handover, 2026-10-29: «в чеке должны быть оба»). The per-thought cap applies to that receipt.
- **The call's ceiling** `max_tokens` = min(the mode's fuse — 2,000 ordinary and the re-ask, 3,000 «Think hard», 400 a worker's answer; what the pet's food pays after the input and the gas share; what its daily cap leaves), so a thought's exact price never exceeds the food or the cap and the project never pays for a thought's tokens (the user, 2026-10-29, defaults accepted).
- **The reservation (Decided by default, replaces «each price is reserved» above):** before the NEAR AI call the server puts the call's ceiling price — this request's input plus `max_tokens` of output — into the pet's unbilled sum; after the response it replaces it with the exact price, or removes it on a failure. Spends of one pet still go one at a time (`Thought queue data`), so a second tab waits and is checked against food and cap with the first already exact. A «Think hard» reserves, on top of its own ceiling, the re-ask's input and 400 output tokens, so a re-ask always has room for a line; the re-ask's own ceiling is min(2,000, what is left of the food and the cap). Alternative rejected: reserving the typical price and capping after the call — two tabs could then push the unbilled sum past the food, and the batch would be rejected on the sum. The reserve only holds the queue: the fullness every viewer sees is food minus the exact unbilled prices, without the reserve of the call in flight, so the scale doesn't dip by a ceiling during each reply and a hungry pet never looks asleep while it answers (the user, 2026-10-29, re-gate add-pet MAJOR 3; `Pet food data`).
- **The hire turn (ADR-011 › «Paid by usage»):** the call where the hirer decides and writes the question is its own thought with its own receipt; the worker's answer is the worker's receipt in the hirer's batch, priced by its usage and paid out of the fee; the hirer's reply after the worker is a second thought.
- **Consequences changed:** a batch rejected for a hire record is resent without it, and the worker's answer the player already got stays in the batch as the hirer's thought, by usage, with no fee (OD-1502 A, replaces «paid by the project» of 2026-10-28). The daily diary thought is paid by usage like any thought; its own debit's gas beyond the share stays the project's (the user, 2026-10-29: short sessions' gas is the project's). A signed answer without the pet's line is not a thought — not shown, not debited, its tokens paid by the project (the user, 2026-10-29, «Принимаю все 6») — for the first three of a pet per UTC day; from the fourth the pet pays it by usage like an ordinary thought, with a receipt in the batch (the user, 2026-10-29, re-gate add-pet MAJOR 2; ADR-005 › «No line»).

## Batches of at most 12, 2026-10-29
The user's decision (build add-pet, critic MINOR 3: «Вписать в спеку»): a session is debited in one or more batches, each with at most N thoughts, and the contract rejects a bigger batch. Everything above stands except where this section says otherwise.
- **Context.** Each thought is one NEP-297 event, and a receipt carries at most 100 logs and 16 kB of them (`near-contract` › Pitfalls; [events](https://docs.near.org/smart-contracts/anatomy/events)). A receipt with two calls (ecdsa signature, signer, two hashes, tokens) is ≈ 0.9 kB [estimate: build `design.md` › Pitfalls], so a long session in one call would fail on the log limit, not on a cap.
- **Decision.** N = 12: `debit_session` accepts 1–12 thoughts; more is rejected whole (`too_many_thoughts`), nothing debited, no receipts. 12 × ≈ 0.9 kB ≈ 11 kB and 12 logs leave room under 16 kB / 100 logs [arithmetic]; the build's sandbox test of a full batch with two calls per thought at maximal field lengths must prove it — if 12 does not fit, a lower N is a spec fix, not a build choice. The server splits a session of more than 12 thoughts into batches of 12 and a remainder, sent one at a time in `debit_id` order (Decided by default: the player sees nothing of it; the explorer shows several debits for one session).
- **Alternatives.** One batch per session, unbounded — rejected: fails past the log limit and the project pays the whole session. N from a test only, not in the spec — rejected by the user's decision: the contract's rejection is a Scenario an attacker can trigger. A batch sent as soon as 12 thoughts are unbilled, mid-session — not taken: the same receipts and caps, and a session is debited when it closes (`Pet food data`).
- **Consequences.** A rejected batch of a split session leaves the batches accepted before it as they are; its thoughts are the project's as before, the next batch reuses its `debit_id`. Gas per thought is about the same in any split (the events dominate), so the gas share of a thought's price (§4) is unchanged [estimate]. The hire records of `add-pet-work` ride in the same batch and share its log budget.

## Four calls a receipt, batches by log bytes, 2026-11-03
The `add-pet-errands` build (plan handover; stage 1, commit c2cdecd). Everything above stands except where this section says otherwise.
- **Amends «One receipt, one or two calls».** A receipt carries 1–4 calls: one; two for a «Think hard» re-ask; up to four for an errand — its search call (`gateway`), a data call, the report and its re-ask (`provider_tee`) (`add-pet-errands` › `Errand debit contract`). The contract's `MAX_CALLS_PER_THOUGHT` is 4; 0 or 5 calls fail the batch whole (`bad_calls`). No new method, field, event or cap; the per-thought cap applies to the whole receipt. Dev: a wasm redeploy, no `migrate` (no layout change); prod: `new` at R1.
- **Measured** (`contract/tests/debit_session.rs`, longest field lengths): one four-call receipt logs 2,265 bytes, a two-call one ≈ 1,250 (12 of them 15,192). The 16,384-byte limit is the sum over the call: 7 four-call thoughts pass (15,855 bytes), 8 fail the whole call («The length of a log message 17968 exceeds the limit 16384»). A four-call thought burns ≈ 1.47 Tgas of the whole transaction (a plain one ≈ 1.25).
- **Amends «Batches of at most 12».** N stays 12 in the contract — 12 two-call thoughts still fit — but 12 is no longer what the server sends: it closes a batch at 12 thoughts or at ≈ 14,000 estimated log bytes, whichever comes first, summing a per-thought estimate (a batch mixes plain thoughts and errands), never counting thoughts only. The 2,384-byte margin covers estimate error. A batch over 16 kB fails whole on the protocol's limit, like a cap: nothing debited, no receipts; an honest server doesn't send one, and one that slips through falls into the rejected-batch path above (the project pays).
- **Decided by default, accepted by the user 2026-11-03 («Принять все»):** keep N = 12 rather than lower it to 7. A lower N would add a debit transaction to every long plain session for no player-visible gain, and a stolen key sending 8+ four-call thoughts is rejected whole by the log limit anyway, with the same outcome as `too_many_thoughts`. The player sees nothing of the split; the explorer shows more debits for a session with errands.
